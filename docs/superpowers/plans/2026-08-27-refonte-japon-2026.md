# Refonte Japon 2026 — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Transformer 8 pages HTML à données dupliquées en 5 pages qui lisent une couche de données unique, sous une direction artistique unique, entièrement utilisables hors-ligne.

**Architecture:** Trois modules ES sous `data/` deviennent la seule source de vérité. Chaque page est une vue qui les lit. Un seul `app.css` remplace les 8 `<style>` inline et `theme.css`. Toutes les dépendances passent dans `vendor/`, toutes les images dans `img/`, et le service worker pré-cache l'ensemble.

**Tech Stack:** Modules ES natifs (pas de build), Alpine.js 3, Leaflet 1.9, Open Props, tuiles Esri Light Gray Canvas, Zen Old Mincho + Inter en WOFF2.

**Spec:** `docs/superpowers/specs/2026-08-27-refonte-japon-2026-design.md`

## Global Constraints

- **Aucune étape de build.** Le dépôt se déploie tel quel sur GitHub Pages. Les scripts de `tools/` sont des one-shot d'auteur, jamais requis pour servir le site.
- **Aucune requête réseau au chargement**, hors tuiles de carte. Pas d'`@import` distant, pas de hotlink d'image, pas de CDN.
- **Zéro `!important`** et zéro `<style>` inline dans les pages. Toute la mise en forme vit dans `app.css`.
- **Une donnée, un endroit.** Un prix, un nom d'hôtel ou une date ne doit apparaître qu'une fois dans `data/`. Tout total est calculé, jamais saisi.
- **Chiffres tabulaires** (`font-variant-numeric: tabular-nums`) sur tout prix, durée, date et compteur.
- **Palette par étape**, valeurs exactes : Tokyo `#2F4858`, Kanazawa `#9A7B2E`, Kyoto `#B7301C`, Osaka `#C2661F`, Hakone `#3E6A85`, excursions `#7C766C`.
- **Accent global** : `#B7301C`. **Papier** `#FBF9F4`. **Encre** `#1C1A17`. **Filets** `#E6E0D4`.
- **Largeurs de vignettes Wikimedia autorisées** : 250, 500, 960, 1280 uniquement. Toute autre largeur renvoie HTTP 400.
- **Le contenu éditorial est conservé mot pour mot.** Cette refonte déplace et remet en forme ; elle ne réécrit aucun texte, conseil ou choix de spot.

```js
// data/spots.js
export const SPOTS = [{ id, name, cityId, category, priority, blurb, img, maps }]

```

Tous les exports sont gelés par `Object.freeze` (profond pour les tableaux d'objets).

**Règles d'extraction** — le point délicat est `cityId` sur les spots :

Dans `guide.html`, les spots vivent dans `.gpanel#t0`..`#t5` (la catégorie), et à l'intérieur un `<h3>` ouvre chaque ville. `cityId` se déduit du dernier `<h3>` rencontré avant la carte. Les intitulés composés se normalisent : `Hakone & Nikko` → `hakone`, `Kanazawa & Nara` → `kanazawa`, `Yokohama` → `tokyo` (c'est une excursion depuis Tokyo). Les autres champs : `data-p` → `priority`, `<b>` → `name`, `<span>` → `blurb`, `img[src]` → `img`, `href` → `maps`.

`HOTELS` se compose de trois sources : le HTML des 6 `.hcard` de `hotels.html` (nom, chambre, prix, accès, images, itinéraire), les coordonnées de `HOTELS[]`/`PTS[]` du même fichier, et les prix de `budget.html` `CATS[0].items[]` — qui doivent **coïncider** avec ceux du HTML ; toute divergence est signalée, pas résolue en silence.

`DAYS` vient de `jour-par-jour.html` `days[]`. Le tableau `DAYS[]` de `aujourdhui.html` est ignoré : c'est le doublon qu'on supprime.

Il importe les trois modules et asserte le tableau « Totaux de référence » ci-dessus, plus les invariants : chaque `STEPS[].hotelId` résout dans `HOTELS` ; chaque `SPOTS[].cityId` et `DAYS[].cityId` existe dans `CITIES` ; `sum(HOTELS[].price) === 3274` ; `sum(STEPS[].nights) === 23` ; aucun `img` ne commence par `http` (assertion qui échouera jusqu'à la Task 2 — la marquer `pending` pour l'instant) ; aucun `id` en double.

- [ ] **Step 2 : Le lancer, vérifier qu'il échoue**

`node tools/verify.mjs` → échec, `data/trip.js` introuvable. C'est le résultat attendu.
